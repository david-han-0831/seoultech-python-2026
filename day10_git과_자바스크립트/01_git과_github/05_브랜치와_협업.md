# 05. 브랜치와 협업

> 혼자 쓸 때는 `add → commit → push` 만으로 충분합니다.
> 브랜치는 **여럿이 같이 할 때** 진가가 나옵니다. 회사에 가면 반드시 씁니다.

---

## 1. 브랜치는 왜 필요한가

돌아가는 서비스에 새 기능을 넣는 상황을 생각해 봅시다.

- 새 기능은 3일 걸립니다.
- 그 3일 동안 코드는 **반쯤 부서진 상태**입니다.
- 그런데 그 사이에 급한 버그 수정도 배포해야 합니다.

브랜치가 없으면 불가능합니다.
브랜치는 **원본을 그대로 둔 채 복사본에서 작업하는 갈래**입니다.

```
main      ●────●────●────────────●────  ← 항상 정상 동작하는 버전
                     \          /
feature/login         ●────●───●        ← 여기서 마음껏 부숴가며 작업
```

작업이 끝나면 `main` 에 **합칩니다(merge)**.

---

## 2. 브랜치 명령어

### 목록 보기

```bash
git branch
```

```
* main
```

`*` 이 지금 내가 있는 브랜치입니다.

### 만들면서 이동 (제일 많이 씀)

```bash
git switch -c feature/login
```

```
Switched to a new branch 'feature/login'
```

- `-c` 는 create 입니다.
- 예전 방식은 `git checkout -b feature/login` 입니다. 둘 다 됩니다.
  `checkout` 은 하는 일이 너무 많아서 `switch` / `restore` 로 분리됐습니다.

### 이동만

```bash
git switch main
```

### 삭제

```bash
git branch -d feature/login
```

(합치지 않은 브랜치를 강제로 지우려면 `-D`)

### 브랜치 이름 규칙

| 형태 | 용도 |
|---|---|
| `feature/기능이름` | 새 기능 |
| `fix/버그이름` | 버그 수정 |
| `docs/문서` | 문서 작업 |

한글·띄어쓰기는 쓰지 마세요.

---

## 3. 브랜치에서 작업하고 합치기

```bash
git switch -c feature/greeting
```

파일을 만들고 커밋합니다.

```bash
echo "안녕하세요" > hello.txt
```

```bash
git add .
```

```bash
git commit -m "인사말 파일 추가"
```

여기서 `main` 으로 돌아가 보세요.

```bash
git switch main
```

```bash
ls
```

**`hello.txt` 가 사라져 있습니다.** 파일이 지워진 게 아니라,
`main` 브랜치 시점에는 그 파일이 아직 없기 때문입니다.
브랜치가 뭔지 몸으로 느껴지는 순간입니다.

### 합치기 (merge)

**합칠 목적지 브랜치로 이동한 뒤** 실행합니다.

```bash
git switch main
```

```bash
git merge feature/greeting
```

```
Fast-forward
 hello.txt | 1 +
```

이제 `main` 에도 `hello.txt` 가 있습니다.

```bash
git branch -d feature/greeting
```

다 쓴 브랜치는 지웁니다.

---

## 4. 충돌(conflict) — 겁먹지 마세요

**같은 파일의 같은 줄**을 두 브랜치에서 서로 다르게 고치면 Git이 판단을 포기합니다.

```
CONFLICT (content): Merge conflict in hello.txt
Automatic merge failed; fix conflicts and then commit the result.
```

파일을 열어 보면 이렇게 되어 있습니다.

```
<<<<<<< HEAD
안녕하세요
=======
반갑습니다
>>>>>>> feature/greeting
```

읽는 법:

- `<<<<<<< HEAD` ~ `=======` : **지금 내 브랜치**의 내용
- `=======` ~ `>>>>>>>` : **합치려는 브랜치**의 내용

### 해결 순서

1. 파일을 열어 **원하는 최종 형태로 직접 고칩니다.**
   `<<<<<<<`, `=======`, `>>>>>>>` **세 줄은 반드시 지웁니다.**
2. ```bash
   git add hello.txt
   ```
3. ```bash
   git commit -m "충돌 해결: 인사말 통일"
   ```

충돌은 에러가 아닙니다. **"둘 중 뭘 쓸지 사람이 정해달라"** 는 요청일 뿐입니다.

### 도저히 모르겠으면 되돌리기

```bash
git merge --abort
```

merge 하기 직전 상태로 완전히 돌아갑니다.

## 5. Pull Request (PR) — 실무의 핵심

회사에서는 `main` 에 **직접 push 하지 못하게 막아둡니다.**
대신 이 흐름을 따릅니다.

```
1. 브랜치 만들기            git switch -c feature/xxx
2. 작업하고 커밋            git add . / git commit
3. 브랜치를 GitHub에 push   git push -u origin feature/xxx
4. GitHub에서 PR 생성        (웹에서 버튼 클릭)
5. 동료가 코드 리뷰          "여기 이렇게 바꾸는 게 어때요?"
6. 승인 후 Merge            (웹에서 버튼 클릭)
7. 브랜치 삭제
```

### PR 만드는 법

1. 브랜치를 push 하면 GitHub 저장소 화면 위에
   **`Compare & pull request`** 노란 버튼이 뜹니다. 클릭.
2. 제목과 설명을 씁니다.
   - **무엇을** 바꿨는지
   - **왜** 바꿨는지
   - 스크린샷이 있으면 첨부
3. **Create pull request**
4. **Files changed** 탭에서 무엇이 바뀌었는지 줄 단위로 보입니다.
   여기에 코멘트를 달 수 있습니다.
5. **Merge pull request** → **Confirm merge**

> PR은 "이 코드 합쳐도 될까요?" 라고 물어보는 **제안서**입니다.
> 신입 개발자가 회사에서 가장 먼저 배우는 것이 PR 쓰기입니다.

### 로컬 정리

merge 후에는 로컬도 최신으로 맞춥니다.

```bash
git switch main
```

```bash
git pull
```

## 6. Issue — 할 일 관리

GitHub의 **Issues** 탭은 무료 협업 도구입니다.

- 버그 신고: "로그인 버튼을 두 번 누르면 에러가 납니다"
- 기능 제안: "다크 모드를 추가하면 좋겠습니다"
- 할 일: "README 작성하기"

팀 프로젝트에서 카톡으로 할 일을 관리하지 말고 Issue를 쓰세요.
누가 무엇을 언제 했는지 전부 남습니다.

> **팁**: 커밋 메시지에 `#3` 처럼 이슈 번호를 적으면 자동으로 연결됩니다.
> 커밋 메시지에 `close #3` 을 넣고 merge하면 그 이슈가 자동으로 닫힙니다.

---

## 7. 팀 프로젝트 최소 규칙

졸업 프로젝트, 공모전에서 그대로 쓰면 됩니다.

1. **`main` 에 직접 push 금지.** 항상 브랜치 → PR.
2. **작업 시작 전 `git pull`.** 이것만 지켜도 충돌의 절반이 사라집니다.
3. **한 브랜치는 한 가지 일만.** "로그인 + 디자인 + 오타수정" 을 한 PR에 넣지 않습니다.
4. **커밋은 작게, 자주.** 하루 한 번 몰아서 커밋하면 되돌릴 수가 없습니다.
5. **`.env` 는 절대 커밋 금지.** 한 번 올라간 키는 유출된 것으로 간주하고 재발급해야 합니다.

## 연습 문제

1. `feature/profile` 브랜치를 만들어 `profile.txt` 를 추가하고 커밋한 뒤 `main` 에 merge 하세요.
2. 일부러 충돌을 만들어 보세요.
   - `main` 에서 `hello.txt` 1번 줄을 "안녕"으로 고치고 커밋
   - `feature/test` 에서 같은 줄을 "반가워"로 고치고 커밋
   - merge 해서 충돌을 확인하고 해결하세요.
3. 브랜치를 GitHub에 push 하고 **PR을 직접 만들어서 merge** 해 보세요.
4. 내 저장소에 Issue를 하나 만들고, 그것을 해결하는 커밋에 `close #1` 을 넣어 보세요.
